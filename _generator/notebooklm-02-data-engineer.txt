## Onderwerpen

### 001 — Wat doet een data engineer?

Kern: Een data engineer bouwt en onderhoudt de pijpleidingen en het platform waarmee data betrouwbaar, veilig en op tijd bij analisten, BI en AI aankomt.

Visual: Stappen: Bronnen —(ophalen)→ Ingest —(landen)→ Opslaan —(opschonen)→ Transformeren —(leveren)→ Serveren
Toelichting: De data engineer is eigenaar van het midden van de keten: van ruwe bron tot bruikbare dataset.

Extra visual: Overlappende gebieden: Softwareengineering, Data & databases, Cloud & infra; in de overlap: Data Engineer
Toelichting: De data engineer zit op het snijvlak van drie vakgebieden.
Extra visual: Centraal begrip Data Engineer, met daaromheen: BI Specialist; Data Analist; Data Scientist; Security; Bron-eigenaren; Platform/IT
Toelichting: Met wie je samenwerkt: je levert data aan iedereen en haalt het bij de bron-eigenaren.

Junior-niveau (de basis):
- Pipeline = geautomatiseerde reeks stappen die data verplaatst en bewerkt.
- Dagelijks werk: Python/SQL schrijven, pipelines bouwen, fouten oplossen, datakwaliteit bewaken.
- Klanten: BI-specialisten, analisten, data scientists.
- Tools: ADF/Glue, Databricks/Spark, dbt, Airflow, Git.

Senior-niveau (verdieping):
- Platform- en architectuurkeuzes: lakehouse, streaming, IaC, security-model.
- Niet-functionele eisen: schaalbaarheid, kosten, herstelbaarheid, SLA's.
- Standaarden en templates zodat het team sneller en consistenter bouwt.
- Data als product: duidelijke eigenaar, contract, documentatie.

Praktijkvoorbeeld:
Een waterschap wil sensordata van gemalen combineren met weerdata. De data engineer bouwt een pipeline die elk kwartier sensordata ophaalt via een API, dagelijks KNMI-data binnenhaalt, alles in Delta-tabellen zet en een goud-tabel levert waarop de BI-specialist het dashboard bouwt.

Begrippen:
- Pipeline: Geautomatiseerde reeks stappen die data verplaatst en bewerkt.
- SLA: Afspraak over beschikbaarheid/tijdigheid (bv. data om 07:00 klaar).
- Data product: Dataset met eigenaar, documentatie en kwaliteitsgarantie.
- API: Interface om data programmatisch op te halen.

Veelgemaakte fouten:
- Alleen bouwen, niet monitoren – fouten merk je dan via boze gebruikers.
- Geen documentatie: niemand anders kan de pipeline onderhouden.
- Elke pipeline anders bouwen in plaats van met herbruikbare patronen.

Ezelsbruggetje: Data engineer = loodgieter van data: als niemand het merkt, doe je het goed.

Oefenvraag uit een sollicitatiegesprek: Wat is volgens jou het verschil tussen een data engineer en een BI-specialist?
Sterke antwoordrichting:
- DE bouwt de betrouwbare datastromen en het platform (techniek, schaal, automatisering).
- BI maakt van die data modellen en dashboards voor de business.
- Overlap in modelleren (Kimball/Data Vault) en SQL – samen één keten.

Snelle controlevragen:
- V: Wat doet een data engineer in één zin? A: Bouwt en onderhoudt de pipelines en het platform waarmee data betrouwbaar bij gebruikers komt.
- V: Wat is een SLA? A: Afspraak over beschikbaarheid of tijdigheid van data.
- V: Wie zijn je 'klanten'? A: BI-specialisten, analisten, data scientists.

Waarom dit telt bij CureLytics: CureLytics levert data engineers én kan complete dataplatformen beheren.

### 002 — Batch versus streaming

Kern: Batch verwerkt data in blokken op vaste momenten (bv. elke nacht); streaming verwerkt elk event zodra het binnenkomt (seconden).

Visual: Vergelijking. Batch: Elke nacht / elk uur; Grote hoeveelheden; Eenvoudiger, goedkoper; ADF, Airflow, Spark. Tegenover Streaming: Continu, real-time; Event voor event; Complexer, duurder; Kafka, Kinesis, Event Hubs.
Toelichting: Vraag altijd: hoe snel moet de data er écht zijn? Meestal is batch genoeg.

Extra visual: Stappen: Producer (sensor/app) → Topic (Kafka) → Streamprocessing → Delta / warehouse → Dashboard / alert
Toelichting: Een typische streaming-architectuur.
Extra visual: Vergelijking. Kappa: Alles is een stream; Eén verwerkingspad; Eenvoudiger. Tegenover Lambda: Batch + streaming; Twee paden; Complex, dubbel werk.
Toelichting: Twee architectuurpatronen voor real-time data.

Junior-niveau (de basis):
- Kafka: platform om berichten (events) op te slaan en door te geven via topics.
- Kinesis (AWS) / Event Hubs (Azure) / Pub/Sub + Dataflow (GCP): managed varianten.
- Producer schrijft naar topic, consumer leest uit topic.
- Voorbeeld streaming: sensordata, klikgedrag, fraudedetectie.

Senior-niveau (verdieping):
- Micro-batch (Spark Structured Streaming) als middenweg.
- Garanties: at-least-once vs exactly-once; idempotente verwerking.
- Windowing, late events, watermarks; schema registry voor contracten.
- Lambda vs Kappa architectuur; kosten en beheerlast afwegen tegen echte behoefte.

Praktijkvoorbeeld:
Een vervoerder wil meldingen als een bus meer dan 5 minuten te laat is. Busposities komen elke 10 seconden binnen via Event Hubs; Spark Structured Streaming berekent vertraging per rit en schrijft afwijkingen naar een alerttabel. De maandrapportage over stiptheid draait gewoon als nachtelijke batch.

Begrippen:
- Topic: Benoemde stroom berichten in Kafka.
- Partition: Deel van een topic voor parallel verwerken.
- Offset: Positie van een consumer in een partitie.
- Exactly-once: Elk event precies één keer verwerkt.
- Watermark (streaming): Hoe lang je wacht op late events.

Codevoorbeeld (Python):
# Spark Structured Streaming: vertraging per rit, elke minuut
from pyspark.sql import functions as F

stream = (spark.readStream.format("kafka")
          .option("subscribe", "busposities").load()
          .select(F.from_json(F.col("value").cast("string"), schema).alias("e")).select("e.*"))

vertraging = (stream.withWatermark("tijd", "5 minutes")
              .groupBy(F.window("tijd", "1 minute"), "rit_id")
              .agg(F.max("vertraging_sec").alias("max_vertraging")))

(vertraging.writeStream.format("delta")
 .option("checkpointLocation", "/chk/vertraging").toTable("goud.vertraging"))

Veelgemaakte fouten:
- Streaming bouwen terwijl elk uur verversen ruim genoeg was.
- Geen checkpointing → na een crash data dubbel of kwijt.
- Geen rekening houden met events die te laat binnenkomen.

Ezelsbruggetje: Batch = de post (één keer per dag), streaming = WhatsApp (direct).

Oefenvraag uit een sollicitatiegesprek: Een klant wil 'real-time dashboards'. Wat doe je?
Sterke antwoordrichting:
- Doorvragen: welk besluit wordt binnen minuten genomen? Vaak volstaat elk kwartier/uur.
- Indien echt nodig: Event Hubs/Kafka → Spark Streaming → Delta → Power BI.
- Benoem extra kosten en beheer.

Snelle controlevragen:
- V: Wat is Kafka? A: Platform om event-berichten op te slaan en te distribueren via topics.
- V: Azure-variant van Kinesis? A: Event Hubs.
- V: Wat is micro-batch? A: Streaming verwerkt in heel kleine batches (bv. elke paar seconden).
- V: Eerste vraag bij 'real-time'? A: Hoe snel moet de data er écht zijn, en welk besluit hangt ervan af?

Waarom dit telt bij CureLytics: Kafka/Kinesis staat in de senior DE-vacature.

### 003 — Data lake, warehouse en lakehouse

Kern: Een data lake slaat alle ruwe bestanden goedkoop op, een warehouse bewaart gestructureerde tabellen voor analyse, en een lakehouse combineert beide.

Visual: Kolommen: Data lake: Alle formaten; Goedkoop; Schema-on-read; Risico: 'data swamp' | Warehouse: Tabellen (SQL); Snel & betrouwbaar; Schema-on-write; Duurder, minder flexibel | Lakehouse: Lake-opslag; + DWH-functies; Delta / Iceberg; Databricks, Fabric
Toelichting: Lakehouse = de flexibiliteit van een lake met de betrouwbaarheid (ACID, schema) van een warehouse.

Extra visual: Tijdlijn: DWH (jaren 90) → Hadoop / lake (± 2010) → Cloud DWH (± 2015) → Lakehouse (± 2020)
Toelichting: Korte geschiedenis: van warehouse via lake naar lakehouse.
Extra visual: Vergelijking. CSV / JSON: Rij- of tekstgebaseerd; Groot, traag; Geen schema. Tegenover Parquet / Delta: Kolomgebaseerd; Gecomprimeerd, snel; Schema + statistieken.
Toelichting: Waarom analytische platformen Parquet gebruiken.

Junior-niveau (de basis):
- Lake-opslag: ADLS Gen2 (Azure), S3 (AWS), GCS (GCP).
- Bestandsformaten: CSV/JSON (ruw) → Parquet (kolomgebaseerd, gecomprimeerd).
- Lakehouse-formaat: Delta Lake (of Apache Iceberg/Hudi).
- Fabric OneLake en Databricks zijn lakehouse-platformen; op GCP: BigQuery (serverless) + BigLake.

Senior-niveau (verdieping):
- Keuze hangt af van data-variëteit, ML-behoefte, skills, kosten en governance.
- Lakehouse voorkomt dubbele opslag (lake + DWH-kopie).
- Governance in de lake: Unity Catalog / Purview, anders wordt het een moeras.
- Open formaten → minder vendor lock-in.

Praktijkvoorbeeld:
Een universiteit heeft een data lake vol CSV's zonder documentatie – niemand weet meer wat actueel is (een 'data swamp'). Migratie naar een lakehouse: alles in Delta, tabellen geregistreerd in Unity Catalog met eigenaar en beschrijving, en toegang per laag.

Begrippen:
- Schema-on-read: Structuur pas bepalen bij het lezen (lake).
- Schema-on-write: Structuur afdwingen bij het schrijven (DWH).
- Parquet: Kolomgebaseerd, gecomprimeerd bestandsformaat.
- Data swamp: Ongeorganiseerd data lake waar niemand meer wijs uit wordt.
- Open table format: Delta, Iceberg, Hudi: tabellen bovenop bestanden.

Veelgemaakte fouten:
- Een lake vullen zonder catalog of eigenaar.
- Alles als CSV opslaan.
- Data dubbel bewaren in lake én warehouse zonder reden.

Ezelsbruggetje: Lake = zolder (alles erin), warehouse = kast met labels, lakehouse = zolder met labels.

Oefenvraag uit een sollicitatiegesprek: Waarom kiezen veel organisaties nu voor een lakehouse?
Sterke antwoordrichting:
- Eén platform voor BI én data science/ML.
- Goedkope opslag met betrouwbaarheid (ACID, time travel).
- Open formaten en schaalbaarheid.

Snelle controlevragen:
- V: Lake vs warehouse? A: Lake: alle formaten, goedkoop, schema-on-read. Warehouse: tabellen, schema-on-write, snel.
- V: Wat voegt een lakehouse toe aan een lake? A: Warehouse-functies: ACID, schema, prestaties.
- V: Waarom Parquet? A: Kolomgebaseerd en gecomprimeerd → snel en goedkoop voor analyses.

Waarom dit telt bij CureLytics: 'modelleren met Data Vault 2.0 of lakehouse-principes' – senior DE-vacature.

### 004 — Medallion-architectuur

Kern: De medallion-architectuur verdeelt een lakehouse in lagen: Brons (ruw), Zilver (opgeschoond) en Goud (klaar voor de business).

Visual: Kolommen: Brons: Ruwe kopie; Zoals uit bron; Append-only → Zilver: Opgeschoond; Ontdubbeld; Gevalideerd → Goud: Business-ready; Ster-schema/KPI; Voor Power BI
Toelichting: Elke laag voegt kwaliteit toe. Fouten in goud? Herbouw vanuit brons.

Extra visual: Trechter, van breed naar smal: Brons – alles (Volume groot, kwaliteit ruw); Zilver – opgeschoond (Ontdubbeld, getypt, gekoppeld); Goud – wat de business gebruikt (Klein, betrouwbaar, gemodelleerd)
Toelichting: Van veel ruwe data naar weinig, zeer betrouwbare data.

Junior-niveau (de basis):
- Brons: data 1-op-1 opslaan + laadmoment → altijd terug te halen.
- Zilver: types corrigeren, dubbelen eruit, bronnen koppelen.
- Goud: geaggregeerd of als ster-schema voor rapportage.
- Komt uit Databricks, nu ook standaard in Microsoft Fabric.

Senior-niveau (verdieping):
- Vergelijkbaar met klassieke lagen: staging → integratie (Data Vault) → datamart (Kimball).
- Kwaliteitschecks bij elke overgang (expectations, dbt tests).
- Zilver kan het Data Vault-model zijn; goud de Kimball-sterren.
- Toegang per laag: analisten alleen goud, engineers alles.

Praktijkvoorbeeld:
Brons: dagelijkse JSON-export van het EPD, ongewijzigd. Zilver: één rij per opname, datums als datum, dubbelingen eruit, cliënt-ID gepseudonimiseerd. Goud: feit_opname + dimensies, klaar voor Power BI. Bij een bug in de zilverlogica herbouw je zilver en goud vanuit brons, zonder het EPD opnieuw te bevragen.

Begrippen:
- Append-only: Alleen toevoegen, nooit wijzigen (brons).
- Conformeren: Data uit bronnen gelijk trekken (types, codes).
- Expectations: Kwaliteitsregels die bij elke laag gecontroleerd worden.

Voorbeeldtabel (Laag | Wie gebruikt het | Kwaliteit | Voorbeeld):
- Brons | Engineers | Ruw | raw_epd_opnames_json
- Zilver | Engineers, data scientists | Gevalideerd | opname (1 rij per opname)
- Goud | BI, analisten | Business-ready | feit_opname, dim_afdeling

Veelgemaakte fouten:
- Transformaties in brons doen – dan ben je de ruwe waarheid kwijt.
- Analisten direct op brons laten werken.
- Geen kwaliteitschecks tussen de lagen.

Ezelsbruggetje: Net als bij de Olympische Spelen: brons → zilver → goud = steeds beter.

Oefenvraag uit een sollicitatiegesprek: Waarom bewaar je de ruwe data in brons als je toch schone data in goud hebt?
Sterke antwoordrichting:
- Herlaadbaarheid: bij een bug in de logica opnieuw verwerken.
- Audit: aantonen wat de bron precies leverde.
- Nieuwe vragen later beantwoorden met velden die je eerst niet gebruikte.

Snelle controlevragen:
- V: Wat staat er in brons? A: Ruwe data zoals uit de bron, append-only.
- V: Wat gebeurt er in zilver? A: Opschonen, ontdubbelen, types corrigeren, koppelen.
- V: Wat staat er in goud? A: Business-ready data: ster-schema's, KPI-tabellen.

Waarom dit telt bij CureLytics: veelgebruikt patroon in Databricks/Fabric-trajecten bij hun klanten.

### 005 — Apache Spark en Databricks

Kern: Spark verwerkt grote datasets door het werk te verdelen over een cluster van machines; Databricks is het cloudplatform om Spark makkelijk te gebruiken.

Visual: Centraal begrip Driver (plan), met daaromheen: Worker 1 partitie A; Worker 2 partitie B; Worker 3 partitie C; Worker 4 partitie D
Toelichting: De driver maakt een plan en verdeelt partities van de data over workers die parallel rekenen.

Extra visual: Vergelijking. Transformaties (lazy): select, filter; join, groupBy; Bouwt alleen een plan. Tegenover Actions (voeren uit): count, show; write, collect; Start de berekening.
Toelichting: Lazy evaluation: niets gebeurt tot je een action aanroept.
Extra visual: Lagen, van boven (dichtst bij de gebruiker) naar onder: Notebooks & Jobs (Waar je werkt); Unity Catalog (governance) (Rechten, lineage, catalog); Spark / Photon (compute) (Clusters, serverless); Delta Lake (opslag) (In jouw cloud-opslag)
Toelichting: Databricks in lagen.

Junior-niveau (de basis):
- Schrijf Spark in PySpark (Python) of Spark SQL.
- DataFrame: tabel-achtige structuur, verdeeld in partities.
- Lazy evaluation: transformaties worden pas uitgevoerd bij een action (write, count, show).
- Databricks: notebooks, clusters, jobs, Unity Catalog.

Senior-niveau (verdieping):
- Shuffles (joins, groupBy) zijn duur – partitionering en broadcast joins gebruiken.
- Data skew herkennen en oplossen (salting, AQE).
- Cluster-sizing en autoscaling, job clusters vs all-purpose (kosten!).
- Unity Catalog voor governance; Delta Live Tables / Lakeflow voor declaratieve pipelines.

Praktijkvoorbeeld:
Een job die 2 miljoen ritten koppelt aan 300 haltes duurt 40 minuten. In de Spark UI blijkt een grote shuffle. Oplossing: de kleine haltes-tabel broadcasten. De job duurt daarna 4 minuten.

Begrippen:
- Driver / executor: Driver plant, executors (workers) voeren uit.
- Partition: Deel van de data dat één taak verwerkt.
- Shuffle: Data herverdelen tussen nodes (duur).
- Broadcast join: Kleine tabel naar elke node kopiëren om shuffle te vermijden.
- Photon: Snelle C++-engine van Databricks.

Codevoorbeeld (Python):
from pyspark.sql import functions as F

ritten = spark.read.table("zilver.ritten")
haltes = spark.read.table("zilver.haltes")          # klein

resultaat = (ritten
    .filter(F.col("datum") >= "2026-01-01")           # vroeg filteren
    .join(F.broadcast(haltes), "halte_id")            # shuffle vermijden
    .groupBy("halte_naam")
    .agg(F.count("*").alias("aantal_ritten")))

resultaat.write.mode("overwrite").saveAsTable("goud.ritten_per_halte")  # action

Veelgemaakte fouten:
- .collect() op een grote dataset → driver loopt vol.
- All-purpose clusters gebruiken voor geplande jobs (duurder dan job clusters).
- Duizenden kleine bestanden laten ontstaan (small files problem).

Ezelsbruggetje: Spark = verhuisploeg: één voorman (driver) en veel sjouwers (workers) tegelijk.

Oefenvraag uit een sollicitatiegesprek: Een Spark-job is traag. Waar kijk je naar?
Sterke antwoordrichting:
- Spark UI: welke stage duurt lang? Veel shuffle of skew?
- Filters vroeg toepassen, alleen benodigde kolommen, broadcast kleine tabellen.
- Bestandsgrootte (small files problem) → OPTIMIZE; clustergrootte bekijken.

Snelle controlevragen:
- V: Wat is lazy evaluation? A: Transformaties bouwen een plan; pas een action voert het uit.
- V: Waarom is een shuffle duur? A: Data moet over het netwerk tussen nodes herverdeeld worden.
- V: Wanneer een broadcast join? A: Als één van de twee tabellen klein is.
- V: Wat is Unity Catalog? A: De governance-laag van Databricks: rechten, lineage, catalog.

Waarom dit telt bij CureLytics: Databricks en Spark staan in de BI- én DE-vacatures.

### 006 — Delta Lake

Kern: Delta Lake is een opslagformaat bovenop Parquet-bestanden dat database-garanties toevoegt: ACID-transacties, schema-handhaving en time travel.

Visual: Lagen, van boven (dichtst bij de gebruiker) naar onder: Delta-tabel (wat je ziet) (SELECT, MERGE, UPDATE); Transaction log (_delta_log) (Wie wijzigde wat, wanneer); Parquet-bestanden (de data) (Kolomgebaseerd, in de lake)
Toelichting: Het transaction log maakt van losse bestanden een betrouwbare tabel.

Extra visual: Tijdlijn: v0 (CREATE) → v1 (INSERT) → v2 (MERGE) → v3 (DELETE) → v4 (OPTIMIZE)
Toelichting: Elke schrijfactie is een nieuwe versie in het transaction log – je kunt naar elke versie terug.

Junior-niveau (de basis):
- ACID: Atomic, Consistent, Isolated, Durable – geen halve schrijfacties.
- Time travel: SELECT * FROM t VERSION AS OF 5 – terug in de tijd.
- MERGE: upsert (insert of update) in één statement.
- Standaardformaat in Databricks en Fabric.

Senior-niveau (verdieping):
- Schema enforcement vs schema evolution (mergeSchema).
- Onderhoud: OPTIMIZE (kleine bestanden samenvoegen), Z-ORDER/liquid clustering, VACUUM.
- Change Data Feed voor incrementele downstream-verwerking.
- Alternatieven: Apache Iceberg, Hudi; Delta UniForm voor interoperabiliteit.

Praktijkvoorbeeld:
Na een foute deploy staan er in de goud-tabel dubbele rijen. Met DESCRIBE HISTORY zie je welke versie het was, en met RESTORE TABLE goud.feit TO VERSION AS OF 41 staat alles binnen een minuut weer goed.

Begrippen:
- Transaction log: _delta_log: lijst van alle wijzigingen aan de tabel.
- Time travel: Een eerdere versie van de tabel opvragen.
- OPTIMIZE: Kleine bestanden samenvoegen tot grotere.
- VACUUM: Oude, niet meer gebruikte bestanden verwijderen.
- Deletion vectors: Rijen markeren als verwijderd zonder bestanden te herschrijven.

Codevoorbeeld (SQL):
MERGE INTO zilver.klant AS doel
USING stg.klant      AS bron
ON    doel.klant_nr = bron.klant_nr
WHEN MATCHED AND doel.hash <> bron.hash THEN UPDATE SET *
WHEN NOT MATCHED                        THEN INSERT *;

DESCRIBE HISTORY zilver.klant;                       -- versies bekijken
SELECT * FROM zilver.klant VERSION AS OF 12;         -- time travel
OPTIMIZE zilver.klant;                               -- kleine bestanden samenvoegen

Veelgemaakte fouten:
- Nooit OPTIMIZE draaien → steeds tragere queries.
- VACUUM met te korte retentie → time travel werkt niet meer.
- Denken dat DELETE meteen fysiek verwijdert (bij deletion vectors niet).

Ezelsbruggetje: Delta = Δ = verschil: het log onthoudt elk verschil, dus je kunt altijd terug.

Oefenvraag uit een sollicitatiegesprek: Hoe zou je SCD type 2 implementeren in Databricks?
Sterke antwoordrichting:
- Delta-tabel met geldig_van, geldig_tot, is_actueel.
- MERGE: gewijzigde rijen afsluiten, nieuwe versies invoegen.
- Of declaratief met Delta Live Tables (APPLY CHANGES / AUTO CDC).

Snelle controlevragen:
- V: Wat betekent ACID? A: Atomic, Consistent, Isolated, Durable.
- V: Hoe ga je terug naar een oude versie? A: Time travel (VERSION AS OF) of RESTORE TABLE.
- V: Wat doet OPTIMIZE? A: Kleine bestanden samenvoegen voor snellere queries.
- V: Waarop is Delta gebouwd? A: Parquet-bestanden + een transaction log.

Waarom dit telt bij CureLytics: Delta Lake staat expliciet in de senior DE-vacature.

### 007 — Orchestratie: Airflow en Data Factory

Kern: Orchestratie bepaalt wanneer en in welke volgorde pipeline-stappen draaien, met afhankelijkheden, herhaalpogingen en monitoring.

Visual: Stappen: Extract A ‖ B (parallel) → Transform (dbt/Spark) → Kwaliteitscheck → Refresh Power BI
Toelichting: Een DAG (Directed Acyclic Graph): taken met afhankelijkheden, zonder lussen. Extract A en B lopen parallel; Transform wacht op beide (fan-in).

Extra visual: Nachtelijke DAG vertakt in: Extract A (API klanten); Extract B (DB orders); Transform (wacht op A + B, dbt build); Publiceren (Power BI refresh, Alert bij fout)
Toelichting: Afhankelijkheden in een DAG: Transform start pas als beide extracts klaar zijn.

Junior-niveau (de basis):
- Airflow: open source, DAG's in Python, scheduler + UI.
- Azure Data Factory: low-code pipelines, copy activity, triggers, linked services.
- AWS Glue: serverless ETL + data catalog.
- Basis: schema (cron), retries, alerts bij falen.

Senior-niveau (verdieping):
- Idempotente taken + backfills (oude periodes opnieuw draaien).
- Metadata-gedreven ADF-pipelines: één pipeline, config-tabel met 100 bronnen.
- Sensors/event-triggers i.p.v. vaste tijden; SLA-monitoring.
- Managed Airflow: Cloud Composer (GCP), MWAA (AWS). Alternatieven: Dagster, Prefect, Databricks Workflows, Fabric Data Pipelines.

Praktijkvoorbeeld:
Een metadata-gedreven ADF-pipeline bij een gemeente: één generieke 'copy'-pipeline leest een configtabel met 85 brontabellen (naam, bron, laadtype, watermark). Een nieuwe tabel toevoegen = één rij in de configtabel, geen nieuwe pipeline.

Begrippen:
- DAG: Directed Acyclic Graph: taken met afhankelijkheden zonder lussen.
- Scheduler: Start taken op tijd of bij een event.
- Backfill: Een pipeline voor oude periodes opnieuw draaien.
- Linked service: ADF-verbinding naar een bron of doel.
- Sensor: Taak die wacht tot een voorwaarde waar is (bv. bestand aanwezig).

Codevoorbeeld (Python):
from airflow import DAG
from airflow.operators.bash import BashOperator
from datetime import datetime

with DAG("nacht", start_date=datetime(2026, 1, 1), schedule="0 2 * * *",
         catchup=False, default_args={"retries": 2}) as dag:
    extract_a = BashOperator(task_id="extract_klanten", bash_command="python extract.py klanten")
    extract_b = BashOperator(task_id="extract_orders",  bash_command="python extract.py orders")
    transform = BashOperator(task_id="dbt_build",       bash_command="dbt build")
    refresh   = BashOperator(task_id="refresh_pbi",     bash_command="python refresh_pbi.py")

    [extract_a, extract_b] >> transform >> refresh

Veelgemaakte fouten:
- Taken bouwen die niet veilig opnieuw kunnen draaien.
- Alles in één gigantische taak stoppen – dan kun je niet gericht herstarten.
- Geen alerting: een gefaalde run wordt pas na dagen ontdekt.

Ezelsbruggetje: Orchestrator = dirigent: speelt zelf geen noot, maar zorgt dat iedereen op tijd inzet.

Oefenvraag uit een sollicitatiegesprek: Wat gebeurt er als een stap in je nachtelijke pipeline faalt?
Sterke antwoordrichting:
- Automatische retries; daarna alert (Teams/mail) naar het team.
- Downstream-taken stoppen, zodat er geen half-bijgewerkte rapporten zijn.
- Oorzaak fixen en idempotent herstarten vanaf de gefaalde stap.

Snelle controlevragen:
- V: Wat is een DAG? A: Graaf van taken met afhankelijkheden, zonder lussen.
- V: Managed Airflow op GCP? A: Cloud Composer.
- V: Wat is een backfill? A: Een pipeline voor historische periodes opnieuw draaien.
- V: Wat is metadata-gedreven? A: Eén generieke pipeline gestuurd door een configtabel.

Waarom dit telt bij CureLytics: ADF, Airflow en Glue staan in de DE-vacatures.

### 008 — dbt: transformeren als software

Kern: dbt (data build tool) laat je transformaties schrijven als SQL SELECT-modellen, met tests, documentatie en versiebeheer – software-engineering voor analytics.

Visual: Stappen: sources (ruwe tabellen) —(source())→ staging modellen —(ref())→ intermediate —(ref())→ marts (feiten/dims)
Toelichting: Modellen verwijzen naar elkaar met ref(); dbt bouwt automatisch de juiste volgorde (lineage).

Extra visual: Kolommen: Generiek: unique; not_null | Relaties: relationships; accepted_values | Eigen: SQL-test; dbt-expectations
Toelichting: Soorten dbt-tests.
Extra visual: Vergelijking. view / table: Elke run volledig; Simpel; Kleine tabellen. Tegenover incremental: Alleen nieuwe rijen; Sneller, goedkoper; Grote feiten.
Toelichting: Materialisaties kiezen.

Junior-niveau (de basis):
- Een model = één .sql-bestand met een SELECT; dbt maakt er een tabel/view van.
- {{ source('erp','klanten') }} voor ruwe tabellen (met freshness-checks); {{ ref('stg_klanten') }} tussen modellen.

Senior-niveau (verdieping):
- Materialisaties: view, table, incremental, ephemeral; snapshots voor SCD2.
- Jinja-macro's en packages (dbt-utils, datavault4dbt).

Praktijkvoorbeeld:
Een team heeft 200 losse SQL-scripts die in een vaste volgorde moeten draaien – niemand durft iets aan te passen. Omzetting naar dbt: elke query wordt een model met ref(), er komen tests op sleutels, en bij elke pull request draait CI. Wijzigingen worden weer gewoon.

Begrippen:
- Model: Eén .sql-bestand met een SELECT.
- ref(): Verwijzing naar een ander model.
- source(): Verwijzing naar een ruwe brontabel.
- Materialization: Hoe een model wordt opgeslagen.
- Snapshot: dbt-mechanisme voor SCD2-historie.

Codevoorbeeld (SQL):
-- models/marts/fct_orders.sql
{{ config(materialized='incremental', unique_key='order_id') }}

select o.order_id, o.klant_id, o.besteldatum, o.bedrag
from {{ ref('stg_orders') }} o
{% if is_incremental() %}
where o.besteldatum > (select max(besteldatum) from {{ this }})
{% endif %}

-- models/marts/schema.yml
-- - name: fct_orders
--   columns:
--     - name: order_id
--       tests: [unique, not_null]

Veelgemaakte fouten:
- Hardgecodeerde tabelnamen in plaats van ref()/source().
- Geen tests – dan is dbt alleen een duurdere manier om SQL te draaien.
- Één enorm model met alle logica in plaats van stappen (staging → marts).

Ezelsbruggetje: dbt = de T in ELT. 'Data Build Tool – Bouw, Test, Documenteer.'

Oefenvraag uit een sollicitatiegesprek: Waarom zou je dbt gebruiken in plaats van losse SQL-scripts?
Sterke antwoordrichting:
- Automatische volgorde en lineage via ref().
- Ingebouwde tests en documentatie → betrouwbaarheid.
- Git, code reviews en CI/CD – samenwerken als software-team.

Snelle controlevragen:
- V: Wat is een dbt-model? A: Een SQL SELECT in een bestand die dbt als tabel/view bouwt.
- V: ref() vs source()? A: ref() tussen modellen, source() naar ruwe brontabellen.
- V: Noem vier standaardtests. A: unique, not_null, relationships, accepted_values.
- V: Hoe doe je SCD2 in dbt? A: Met snapshots.

### 009 — Python & SQL in pipelines: idempotentie

Kern: Een goede pipeline is idempotent: hem twee keer draaien geeft hetzelfde resultaat als één keer – geen dubbele rijen, geen kapotte data.

Visual: Vergelijking. Niet idempotent: INSERT bij elke run; Run 2× = dubbele data; Handmatig opruimen. Tegenover Idempotent: MERGE / overwrite partitie; Run 2× = zelfde resultaat; Veilig herstarten.
Toelichting: Idempotentie maakt retries, backfills en herstel veilig.

Extra visual: Stappen: Run voor 2026-10-30 → Overschrijf partitie 30-10 → Run nogmaals (retry) → Zelfde resultaat
Toelichting: Idempotent laden per datumpartitie: opnieuw draaien is veilig.

Junior-niveau (de basis):
- Python voor: API's aanroepen, bestanden verwerken, PySpark, Airflow-DAG's.
- Libraries: pandas/polars, requests, pyspark.
- Gebruik Git, functies en logging – geen losse notebooks zonder structuur.
- Technieken: MERGE op sleutel, partitie overschrijven per datum.

Senior-niveau (verdieping):
- Testen: unit tests (pytest) voor transformatielogica, data tests voor output.
- Configuratie scheiden van code; secrets in Key Vault, nooit in code.
- Packaging en hergebruik (wheels, shared libraries, Databricks Asset Bundles).
- Incrementeel laden met watermarks/CDC, idempotent ontworpen.

Praktijkvoorbeeld:
Een pipeline faalt halverwege en wordt automatisch herstart. Omdat hij met INSERT werkte, staan de eerste 50.000 rijen er nu dubbel in en kloppen de omzetcijfers niet. Na ombouw naar MERGE op order_id is een retry altijd veilig.

Begrippen:
- Idempotent: Meerdere keren uitvoeren = zelfde resultaat als één keer.
- Upsert: Update als het bestaat, insert als het nieuw is.
- Run-datum: Expliciete datum waarvoor een run draait (niet 'nu').
- pytest: Python-testframework.

Codevoorbeeld (Python):
def laad_dag(spark, run_datum: str) -> None:
    """Idempotent: overschrijft alleen de partitie van run_datum."""
    df = (spark.read.table("brons.orders")
          .where(f"order_datum = '{run_datum}'")
          .dropDuplicates(["order_id"]))
    (df.write.format("delta").mode("overwrite")
       .option("replaceWhere", f"order_datum = '{run_datum}'")
       .saveAsTable("zilver.orders"))

def test_dubbel_draaien_geeft_zelfde_aantal(spark):
    laad_dag(spark, "2026-10-30"); a = spark.table("zilver.orders").count()
    laad_dag(spark, "2026-10-30"); b = spark.table("zilver.orders").count()
    assert a == b

Veelgemaakte fouten:
- datetime.now() in de logica → herstarten op een andere dag geeft andere data.
- Secrets in code zetten.
- Notebooks zonder functies, tests of versiebeheer.

Ezelsbruggetje: Idempotent = liftknop: tien keer drukken, de lift komt toch maar één keer.

Oefenvraag uit een sollicitatiegesprek: Hoe zorg je dat je pipeline veilig opnieuw kan draaien?
Sterke antwoordrichting:
- Upserts met MERGE op een unieke sleutel, of partitie per dag overschrijven.
- Geen afhankelijkheid van 'nu'-tijd; werk met een expliciete run-datum.
- Test het: draai twee keer en vergelijk aantallen.

Snelle controlevragen:
- V: Wat betekent idempotent? A: Twee keer draaien geeft hetzelfde resultaat als één keer.
- V: Noem twee idempotente technieken. A: MERGE op een sleutel; partitie overschrijven per datum.
- V: Waarom een expliciete run-datum? A: Zodat herstarts en backfills hetzelfde resultaat geven.

Waarom dit telt bij CureLytics: 'processen automatiseren met Python, SQL en Airflow' – medior DE-vacature.

### 010 — Datakwaliteit en monitoring

Kern: Datakwaliteit = data is juist, volledig, tijdig, consistent, uniek en valide; je bewaakt dat met automatische checks en alerts in elke pipeline.

Visual: Centraal begrip Datakwaliteit, met daaromheen: Juistheid; Volledigheid; Tijdigheid; Consistentie; Uniciteit; Validiteit
Toelichting: Zes klassieke dimensies van datakwaliteit.

Extra visual: Stappen: Nieuwe data → Checks (tests) → Goed → door naar zilver → Fout → quarantaine → Alert + issue
Toelichting: Kwaliteitspoort in de pipeline: foute records apart zetten in plaats van alles stoppen.
Extra visual: Centraal begrip Observability, met daaromheen: Versheid; Volume; Schema; Distributie; Lineage
Toelichting: De vijf pijlers van data observability.

Junior-niveau (de basis):
- Checks: geen NULL in verplichte velden, geen dubbele sleutels, waarden binnen bereik.
- Aantallen vergelijken met de bron (reconciliatie).
- Versheid: is de data van vandaag binnen?
- Tools: dbt tests, Great Expectations, Databricks expectations.

Senior-niveau (verdieping):
- Data observability: volume, versheid, schema-wijzigingen en distributie automatisch volgen.
- Data contracts met bron-eigenaren: afspraken over schema en kwaliteit.
- Quarantaine-tabellen voor foute records i.p.v. alles stoppen.
- Kwaliteit is ook organisatie: data stewards, issue-proces, KPI's op kwaliteit.

Praktijkvoorbeeld:
Op maandag levert het HR-systeem plots 40% minder rijen. Een volumecheck vangt dit om 06:30 af; het dashboard toont een waarschuwing 'data van vrijdag' in plaats van foute cijfers, en het team belt de bron-eigenaar vóór de managers om 09:00 kijken.

Begrippen:
- Reconciliatie: Aantallen/totalen vergelijken met de bron.
- Data contract: Afspraak met de bron over schema en kwaliteit.
- Quarantaine: Tabel waarin afgekeurde records worden geparkeerd.
- Freshness: Hoe actueel de data is.

Codevoorbeeld (SQL):
-- Eenvoudige kwaliteitschecks (falen = rijen teruggeven)
SELECT 'dubbele sleutel' AS check, order_id FROM zilver.orders GROUP BY order_id HAVING COUNT(*) > 1
UNION ALL
SELECT 'bedrag negatief', order_id FROM zilver.orders WHERE bedrag < 0
UNION ALL
SELECT 'niet ververst', NULL WHERE (SELECT MAX(laad_tijd) FROM zilver.orders) < DATEADD(hour, -26, GETDATE());

Veelgemaakte fouten:
- Alleen testen of de pipeline draait, niet of de data klopt.
- Bij elke fout de hele pipeline stoppen in plaats van quarantaine.
- Kwaliteitsproblemen stil oplossen zonder de bron-eigenaar te informeren.

Ezelsbruggetje: J-V-T-C-U-V: 'Jan Vult Thee, Cor Uit Volendam' – Juist, Volledig, Tijdig, Consistent, Uniek, Valide.

Oefenvraag uit een sollicitatiegesprek: Een manager zegt: 'de cijfers in het dashboard kloppen niet'. Wat doe je?
Sterke antwoordrichting:
- Concreet maken: welk getal, wat verwacht hij, welke bron vertrouwt hij?
- Terugtraceren via lineage: goud → zilver → brons → bron; waar wijkt het af?
- Fix + test toevoegen zodat het niet opnieuw gebeurt; communiceer terug.

Snelle controlevragen:
- V: Noem de zes kwaliteitsdimensies. A: Juistheid, volledigheid, tijdigheid, consistentie, uniciteit, validiteit.
- V: Wat is data observability? A: Automatisch volgen van versheid, volume, schema en distributie.
- V: Wat is een data contract? A: Afspraak met de bron-eigenaar over schema en kwaliteit.

Waarom dit telt bij CureLytics: 'datakwaliteit monitoren' staat letterlijk in de medior DE-vacature.

### 012 — Security: IAM, RBAC en least privilege

Kern: IAM regelt wie (identiteit) wat mag (autorisatie); met RBAC ken je rechten toe aan rollen in plaats van personen, volgens het principe van least privilege.

Visual: Stappen: Gebruiker / service —(lid van)→ Groep (Entra ID) —(krijgt)→ Rol (bv. Reader) —(op)→ Resource (tabel, lake)
Toelichting: Rechten via groepen en rollen – nooit rechtstreeks aan individuen.

Extra visual: Lagen, van boven (dichtst bij de gebruiker) naar onder: Data (RLS, maskering, grants) (Wie ziet welke rijen/kolommen?); Identiteit (Entra ID, rollen) (Wie ben je, wat mag je?); Netwerk (private endpoints) (Waar mag verkeer vandaan?); Infrastructuur (encryptie) (Opslag versleuteld)
Toelichting: Defense in depth: meerdere beveiligingslagen.
Extra visual: Kolommen: Engineers: Schrijven brons; Schrijven zilver | Analisten: Lezen goud | Pipelines: Managed identity; Alleen eigen pad | Lezers: Alleen rapporten
Toelichting: Voorbeeld rollenmodel voor een lakehouse.

Junior-niveau (de basis):
- Authenticatie = wie ben je? Autorisatie = wat mag je?
- Least privilege: precies genoeg rechten, niet meer.
- Service principals / managed identities voor pipelines (geen persoonlijke accounts).
- Encryptie at rest en in transit is standaard in de cloud.

Senior-niveau (verdieping):
- Lagen: netwerk (private endpoints, VNet), identiteit (Entra ID), data (Unity Catalog grants, RLS/CLS).
- ABAC (attribuut-gebaseerd) en dynamische maskering voor gevoelige kolommen.
- Secrets in Key Vault / Secrets Manager; rotatie.
- Audit logging en periodieke access reviews (ISO 27001, BIO).
- AWS: IAM-rollen/policies (assume role), Lake Formation voor tabel-/kolomrechten. GCP: IAM op project/dataset, BigQuery column-level security. Concept blijft: identiteit → rol → scope.

Praktijkvoorbeeld:
Een pipeline draaide onder het persoonlijke account van een vertrokken medewerker. Toen dat account werd uitgeschakeld, stopte alles. Oplossing: managed identities voor alle pipelines, rechten via groepen, en een kwartaal-access-review.

Begrippen:
- IAM: Identity & Access Management.
- RBAC: Rechten via rollen.
- ABAC: Rechten op basis van attributen (bv. gevoeligheidslabel).
- Least privilege: Precies genoeg rechten.
- Managed identity: Identiteit voor een dienst, zonder wachtwoord.

Codevoorbeeld (SQL):
-- Unity Catalog: rechten per groep en laag
GRANT USE CATALOG ON CATALOG zorg TO `analisten`;
GRANT SELECT ON SCHEMA zorg.goud TO `analisten`;
GRANT ALL PRIVILEGES ON SCHEMA zorg.zilver TO `data-engineers`;

-- kolom maskeren voor wie niet in de groep zit
CREATE FUNCTION zorg.mask_bsn(bsn STRING) RETURN
  CASE WHEN is_account_group_member('privacy-ok') THEN bsn ELSE '***' END;
ALTER TABLE zorg.zilver.client ALTER COLUMN bsn SET MASK zorg.mask_bsn;

Veelgemaakte fouten:
- Rechten aan personen geven in plaats van aan groepen.
- Iedereen 'Contributor' geven omdat het makkelijk is.
- Pipelines onder persoonlijke accounts laten draaien.

Ezelsbruggetje: RBAC = sleutelbos per functie: de schoonmaker krijgt andere sleutels dan de directeur.

Oefenvraag uit een sollicitatiegesprek: Hoe richt je toegang in op een lakehouse met gevoelige zorgdata?
Sterke antwoordrichting:
- Groepen per rol (engineer, analist, lezer) via Entra ID; rechten per laag (brons/zilver/goud).
- Gevoelige kolommen maskeren/pseudonimiseren; RLS waar nodig.
- Managed identities voor pipelines, private endpoints, audit logs.

Snelle controlevragen:
- V: Authenticatie vs autorisatie? A: Authenticatie = wie ben je; autorisatie = wat mag je.
- V: Wat is least privilege? A: Alleen de rechten die nodig zijn, niet meer.
- V: Waarom managed identities? A: Geen wachtwoorden in code en niet afhankelijk van personen.
- V: AWS-tool voor tabel/kolomrechten op de lake? A: Lake Formation.

Waarom dit telt bij CureLytics: 'IAM/RBAC-modellen opzetten en databeveiliging waarborgen' – senior DE-vacature.

### 013 — Governance, compliance en metadata

Extra visual: Kolommen: Openbaar: Open data | Intern: Bedrijfsdata | Vertrouwelijk: Personeel, financiën | Bijzonder: Gezondheid, BSN
Toelichting: Dataclassificatie: hoe gevoeliger, hoe strenger toegang en logging.

Junior-niveau (de basis):
- Metadata = data over data: beschrijving, eigenaar, type, gevoeligheid.
- Lineage = herkomst: van welke bron via welke stappen komt dit veld?
- Data catalog: Microsoft Purview, Unity Catalog, AWS Glue Data Catalog.
- ISO 27001 = norm voor informatiebeveiliging: een risicogebaseerd ISMS (Plan-Do-Check-Act).

Senior-niveau (verdieping):
- Classificatie van data (openbaar, intern, vertrouwelijk, bijzonder) en labels die doorwerken in toegang.
- Bewaartermijnen en verwijderen (recht op vergetelheid) technisch borgen.
- Privacy by design: pseudonimiseren in brons, minimaliseren in goud.
- Data mesh: governance federatief – domeinen eigenaar, centrale standaarden.
- ISO 27001:2022: 93 beheersmaatregelen in Annex A (toegang, logging, leveranciers), externe audit. BIO2 bouwt op ISO 27002:2022. Jij levert bewijs: access reviews, logging, change-proces.

Praktijkvoorbeeld:
Een auditor vraagt: 'Waar komt het getal 1.243 wachtenden in het bestuursrapport vandaan?' Dankzij lineage in Purview toon je in twee minuten de route van bron tot rapport, inclusief welke transformaties en wie eigenaar is.

Begrippen:
- Metadata: Data over data: eigenaar, beschrijving, type, gevoeligheid.
- Lineage: Herkomst en route van data.
- Data catalog: Zoekbare inventaris van datasets.
- ISMS: Information Security Management System (ISO 27001).
- Classificatie: Data indelen naar gevoeligheid.

Veelgemaakte fouten:
- Governance als papieren beleid zonder technische borging.
- Geen eigenaar per dataset.
- Recht op vergetelheid alleen in de bron uitvoeren, niet in alle lagen en back-ups.

Ezelsbruggetje: Wat – Waar – Wie – Wet: welke data, waar vandaan, wie is eigenaar, voldoet het aan de wet?

Oefenvraag uit een sollicitatiegesprek: Hoe ga je in een pipeline om met het recht op vergetelheid (AVG)?
Sterke antwoordrichting:
- Weten waar persoonsgegevens staan (catalog + lineage).
- Verwijderproces door alle lagen: DELETE → bij deletion vectors REORG TABLE … APPLY (PURGE) → VACUUM na de retentieperiode; ook Change Data Feed en back-ups meenemen.
- Pseudonimiseren met een apart beheerde sleuteltabel – let op: dat blijft persoonsdata. Bij vergetelheid wis je de identiteit in de sleuteltabel (of de sleutel: 'crypto-shredding') plus direct identificerende velden in alle lagen.

Snelle controlevragen:
- V: Wat is lineage? A: De herkomst en route van data van bron tot rapport.
- V: Noem twee data catalogs. A: Microsoft Purview, Unity Catalog (of AWS Glue Data Catalog).
- V: Wat is ISO 27001? A: Norm voor een risicogebaseerd ISMS met beheersmaatregelen (Annex A).
- V: Hoeveel maatregelen telt Annex A (2022)? A: 93.

Waarom dit telt bij CureLytics: 'kennis van GDPR, ISO 27001 en metadata management' – senior DE-vacature.

### 014 — CI/CD en DataOps

Kern: CI/CD test en rolt wijzigingen automatisch uit (dev → test → prod); DataOps past die werkwijze toe op datapipelines voor snellere én betrouwbaardere levering.

Visual: Stappen: Branch + commit → Pull request + review → CI: tests (dbt, pytest) → Deploy test → Deploy prod
Toelichting: Niets gaat naar productie zonder review en geslaagde tests.

Extra visual: Cyclus (herhaalt zich): Plan → Code → Test → Deploy → Monitor → terug naar het begin
Toelichting: De DataOps-cyclus: monitoring voedt de volgende planning.
Extra visual: Kolommen: Feature branch: Ontwikkelen; Lokaal testen → Pull request: Review; CI-tests → main: Deploy test; Deploy prod
Toelichting: Van branch naar productie.

Junior-niveau (de basis):
- Git: branches, commits, pull requests, merge.
- CI = Continuous Integration (automatisch testen), CD = Continuous Delivery/Deployment (uitrollen).
- Tools: Azure DevOps, GitHub Actions, GitLab CI.
- Aparte omgevingen: dev, test/acceptatie, productie (DTAP/OTAP).

Senior-niveau (verdieping):
- Branching-strategie (trunk-based vs GitFlow).
- Databricks Asset Bundles, dbt CI, ADF ARM/Bicep-deploys, Power BI deployment pipelines.
- Testdata en data-diffs tussen omgevingen.
- Monitoring en incident-proces na deploy (DataOps-feedbackloop).

Praktijkvoorbeeld:
Een collega past een dbt-model aan en opent een pull request. CI bouwt alleen de gewijzigde modellen en hun afnemers (slim CI), draait alle tests en ziet dat een not_null-test faalt. De fout komt nooit in productie.

Begrippen:
- CI: Continuous Integration: automatisch bouwen en testen bij elke wijziging.
- CD: Continuous Delivery/Deployment: automatisch uitrollen.
- Pull request: Verzoek om code samen te voegen, met review.
- OTAP: Ontwikkel, Test, Acceptatie, Productie.
- Rollback: Terug naar de vorige werkende versie.

Codevoorbeeld (YAML):
# .github/workflows/dbt-ci.yml
on: pull_request
jobs:
  dbt:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install dbt-databricks
      - run: dbt deps
      - run: dbt build --select state:modified+ --defer --state ./prod-artifacts
        env:
          DBT_TOKEN: ${{ secrets.DBT_TOKEN }}

Veelgemaakte fouten:
- Direct in productie wijzigen ('even snel').
- CI zonder echte tests.
- Geen rollback-plan bij een deploy.

Ezelsbruggetje: OTAP: Ontwikkel, Test, Acceptatie, Productie – nooit direct van O naar P.

Oefenvraag uit een sollicitatiegesprek: Hoe breng je een wijziging aan een pipeline veilig naar productie?
Sterke antwoordrichting:
- Feature branch, pull request met review.
- Automatische tests in CI; deploy naar test en valideer met echte(-achtige) data.
- Goedkeuring → prod; monitoren en rollback-plan klaar.

Snelle controlevragen:
- V: Wat is CI? A: Automatisch bouwen en testen bij elke wijziging.
- V: Wat betekent OTAP? A: Ontwikkel, Test, Acceptatie, Productie.
- V: Wat is slim CI in dbt? A: Alleen gewijzigde modellen en hun afnemers bouwen en testen.

Waarom dit telt bij CureLytics: professioneel werken in Agile teams bij klanten vraagt om deze discipline.
